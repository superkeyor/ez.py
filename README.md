# ez

[![PyPI Version](https://img.shields.io/pypi/v/ez.svg)](https://pypi.org/project/ez/)
[![Python Versions](https://img.shields.io/pypi/pyversions/ez.svg)](https://pypi.org/project/ez/)
[![License: AGPLv3+](https://img.shields.io/badge/License-AGPL%20v3%2B-blue.svg)](https://www.gnu.org/licenses/agpl-3.0.html)

A cross-platform Python utility library for easy shell interaction and common programming tasks on Linux, macOS, and Windows.

---

## Installation

```bash
pip install ez
```

Requires Python 3.11+.

For packages used by external scripts (Flask and its extensions, Gunicorn,
cachelib, DuckDB, parse, PyYAML, xmltodict, and macOS-only imessage_reader):

```bash
pip install 'ez[extra]'
```

These packages are optional and are not installed with plain `ez`.

---

## Quick Start

```python
from ez import *

# File operations
files = ls('~/Documents', r'\.py$')
cp('source.txt', '~/backup/')
mv('old_name.txt', 'new_name.txt')
rm('temp/')

# Path utilities
print(cwd())                            # current working directory
print(jp('~', 'Documents', 'file'))     # join path components
print(sp('/path/to/file.txt'))          # => ['/path/to', 'file', '.txt']

# Execute shell commands
execute('ls -la')
output = execute2('echo hello')
esp('echo %s', 'world')

# Read/write spreadsheets
data = readx('data.xlsx')
savex('output.xlsx', data, header=['Name', 'Age'])
```

## Usage Details

### Installing Packages

```python
import ez

ez.require("gTTS", confirm=False, quiet=True)
ez.require("ffmpeg", confirm=False, channel="conda", quiet=True)
```

`quiet=True` hides routine helper and installer output; confirmation prompts and
errors remain visible, including captured installer output on failure. The
default `quiet=False` preserves live output. Use `confirm=False` to skip prompts.

### Documents to Markdown

```python
import ez

markdown = ez.pptx2md('talk.pptx')  # prints to stdout and returns the Markdown
markdown = ez.pptx2md(
    'talk.pptx', note=True, slides='1-3,5', markers=False,
    images=True, output='talk.md', overwrite=True,
)
```

All four converters return the Markdown string and print it when `output=None`.
With `output='file.md'`, they write UTF-8 instead of printing. Existing output files
raise `FileExistsError` unless `overwrite=True`; replacing the input document is
always rejected, including symlink/hard-link aliases.

#### OCR for embedded Office images

`pptx2md`, `docx2md`, and `xlsx2md` can recognize text inside embedded images
using Apple's local Vision framework. OCR is disabled by default, requires
macOS, and sends no document data to a network service. It is supported on
Intel macOS Big Sur and Apple Silicon macOS Sonoma.

The Vision binding is installed as a platform-specific project dependency on
macOS only. Use `ocr=True` in Python or `--ocr` on the command line.
Recognition defaults to Apple's more comprehensive `accurate` mode; choose
`fast` explicitly when speed matters more. OCR recognizes English by default;
use `ocr_language="chinese"` / `--ocr-language chinese` for Simplified
Chinese, or `"both"` for both English and Simplified Chinese:

```python
markdown = ez.pptx2md(
    "talk.pptx", ocr=True, ocr_language="english", ocr_mode="accurate",
)
```

```bash
docx2md report.docx --ocr --ocr-mode fast
xlsx2md data.xlsx --ocr --ocr-language chinese
xlsx2md data.xlsx --ocr
```

The `--ocr-mode`, `--ocr-language`, and `--ocr-failed-dir` CLI options require
`--ocr`. Supported language names are `english`, `chinese` (Simplified
Chinese), and `both`.
To keep copies of images OCR could not process, set `ocr_failed_dir` in Python
or use `--ocr-failed-dir DIR`; the directory is created as needed and existing
files are not overwritten by default. Passing `overwrite=True` in Python or
`--overwrite` on the command line replaces an existing failed-image file with
the same generated name (as well as allowing replacement of an existing
Markdown output file). Successfully processed images with no recognized text
are not considered failures. PowerPoint pictures linked to external files are
silently ignored because their image data is not embedded in the presentation.
PowerPoint OCR uses each picture's visible crop. It masks parts covered by
later, unrotated, fully opaque rectangular solid-fill shapes only when the
picture itself is unrotated and unflipped. Transparent fills, rotated shapes,
and other non-rectangular or non-solid effects are not treated as covers. This
crop/mask handling only considers shapes in the same shape group and does not
resolve group transforms. If a cropped or covered image cannot be rendered for
filtering, it is skipped with a warning rather than OCRing hidden content. This
crop/mask handling is specific to PowerPoint; Word and Excel OCR the full
embedded image and do not account for document crop settings or overlaid
shapes. Enhanced Metafiles that contain an embedded PDF are rasterized locally
with PyMuPDF before OCR; if OCR fails, the rasterized PNG is saved to
`ocr_failed_dir` instead of the original metafile.
OCR text is added after its slide in PowerPoint, after its image in Word, and
under a worksheet heading labeled with the nearest image anchor in Excel.
Charts and other non-image objects are not OCRed. On non-macOS systems,
conversions without `ocr=True` / `--ocr` are unchanged; explicitly requesting
OCR reports that Apple Vision is unavailable. A document with no embedded
images is converted normally; invalid or zero-sized embedded images produce a
warning and are skipped rather than failing the whole conversion. CLI OCR
warnings use a concise `<command>: warning: ...` format without Python source
locations. They identify the source file and the embedded image's slide,
worksheet, or document context.

#### PDF annotations

Extract highlights and annotations with the installed command:

```bash
pdfannot paper.pdf
pdfannot first.pdf second.pdf --output-file notes.md
pdfannot papers --recursive --output-dir notes --no-update-metadata
```

| Python argument (default) | CLI flag | Effect |
|---|---|---|
| `pdfpath` | `INPUT [INPUT ...]` | PDF path or folder; the CLI also supports multiple inputs and wildcard patterns. |
| `mdpath=None` | `-o`, `--output-file` | Python prepends to this file and still prints; the CLI uses the shared output rules below instead. |
| `mode=2` | `--mode {0,1,2}` | Control the legacy skip rules; default is always to extract. |
| `update_metadata=True` | `--update-metadata`, `--no-update-metadata` | Mark extracted PDFs as processed, or opt out to leave them unchanged. |

- Mode `0` applies the timestamp heuristic and skips PDFs whose producer metadata
  already contains `PyHighlightExtractor`.
- Mode `1` applies only the timestamp heuristic: skip when modification time minus
  creation time is greater than -5 and less than 60 seconds.
- Mode `2` bypasses both skip rules. PDFs without annotations produce no content.

**Both interfaces update PDF metadata by default.** The processed marker is added
after successful extraction, before output writing. A later output-write failure
does not roll back this change. No metadata write occurs for skipped PDFs, PDFs
without annotations, or PDFs already carrying the marker. Use
`--no-update-metadata` (Python: `update_metadata=False`) for read-only extraction.
Other metadata fields are retained. Metadata-write errors are reported; in CLI
batches, other inputs continue and the command exits nonzero.

```python
ez.pdfannot('paper.pdf', mode=2, update_metadata=False)
ez.pdfannot('paper.pdf', mdpath='notes.md')  # prepends and also prints
```

The Python function still returns `None`, accepts PDF folders, and prepends new
Markdown to an existing `mdpath`. Its old `force` argument is now named `mode`,
and its default changed from `1` to `2`; update calls using `force=` to `mode=`.
The third positional argument still selects the mode. The CLI never prepends to
an existing output file.

#### Batch commands and output

All five installed commands accept multiple files, folders, and wildcard patterns.
The four Python document converters still process one file per call; Python
`pdfannot` retains its existing folder support.

```bash
pptx2md *.pptx --output-dir markdown --images
docx2md first.docx second.docx --output-dir markdown
docx2md first.docx second.docx --output-file combined.md --overwrite
pdf2md reports --recursive --output-dir markdown
pdf2md "reports/**/*.pdf" --recursive --output-dir markdown
xlsx2md workbooks --output-dir markdown --sheets Summary
pdfannot first.pdf second.pdf -o annotations.md --no-update-metadata
```

- More than one distinct input requires either `-o`/`--output-file FILE` or
  `--output-dir DIR`. These destinations are mutually exclusive.
- `--output-file` combines multiple documents in discovery order, adding a source
  heading (relative to the common input root) before each document. The destination
  is written once with all successful results, not overwritten for each input.
  Single-document output retains its existing formatting, without an extra heading.
- `--output-dir` writes one `.md` file per input. A single input without either
  destination prints to stdout.
- Folders are scanned for the command's file extension, case-insensitively.
  Use `--recursive` for nested folders or quoted `**` patterns. Recursive
  discovery does not follow directory symlinks.
- Output folders are created as needed. Structure is preserved relative to the
  common ancestor of input roots: a folder's root is itself, an explicit file's
  root is its parent, and a wildcard's root is its non-wildcard directory prefix.
  For example, `pdf2md reports --recursive --output-dir markdown` maps
  `reports/a/report.pdf` to `markdown/a/report.md`. Explicit inputs
  `a/report.pdf b/report.pdf` map to `markdown/a/report.md` and
  `markdown/b/report.md`, rather than overwriting one another.
- Repeated files and file aliases are converted once. Outputs colliding with
  another destination or any source document are rejected, even with `--overwrite`.
  This protects output destinations; `pdfannot` may separately update source
  metadata unless explicitly disabled.
- All command options apply to every input. Discovery/extraction/output
  failures are reported to stderr while other files continue. A final summary
  reports succeeded/failed counts; any failure produces a nonzero exit status.
  Unmatched patterns and folders with no matching files are errors, not silent
  successes. Combined output includes successful inputs even if others fail; the
  exit status is still nonzero. If all inputs fail, no combined file is created
  or replaced. An empty extraction is a success, not a failure. Unexpected
  programming errors remain visible.
- `--overwrite` permits replacing existing output files; otherwise they are
  reported as failures. It does not append. Batch output goes to files, not stdout.
- Breaking CLI change: `--output`, `--force`, and `-f` are no longer accepted.
  Use `-o`/`--output-file` and `--overwrite`.

#### Installed commands and future CLI tools

Install this version of the package to generate all five commands:

```bash
python -m pip install .
# Or, for local development:
python -m pip install -e .
```

Activate the Python environment containing `ez`, or put its executable directory
on `PATH`. All commands support `-o`/`--output-file`, `--output-dir`,
`--overwrite`, and `-h`/`--help`. Running any registered command without arguments
shows help and exits successfully. Importing or directly running `ez/ez.py` does
not launch a CLI. An existing shell function named `pdfannot` shadows the installed
command; remove it from your shell configuration and run `unset -f pdfannot` in
the current Bash session, or invoke the installed executable by its full path.

`_CLI_COMMANDS` in `ez/ez.py` is the single registry of exported tools. To expose
another tool, add its function and a registry entry with `function`, `description`,
`arguments`, `notes`, and `examples`; optional `groups` reuse argument groups.
Each argument is a pair of flag/name strings and an argparse-options dictionary.
Use the strings `"str"`, `"int"`, or `"float"` for typed arguments. Unspecified
options are omitted from the function call, preserving the function's defaults.
Command names may differ from function names; registered targets must accept the
parsed arguments as keywords. The dispatcher ignores normal return values and
exits successfully after a successful call.

Batch support is opt-in: these command entries also specify `batch` metadata
(`input` parameter, supported `extension`, and expected document `errors`) and
use the shared `batch` argument group. Tools without this metadata retain normal
single-call dispatch. Batch entries specify an `output_format` from
`_CLI_OUTPUT_FORMATS`, which supplies the output extension and combination
function. Current commands use the Markdown format; the shared discovery,
registration, output paths, staging, and error reporting are not named or
hard-coded as Markdown-only infrastructure. Combination formatting belongs to
the configured format.

[`ez/prepublish.py`](ez/prepublish.py) reads the literal registry without importing
runtime dependencies and generates the marked `[project.scripts]` table in
[`pyproject.toml`](pyproject.toml), targeting the general `_cli` dispatcher. Run
the hook and reinstall the package after adding a command. No new wrapper files or shell functions are
needed. Extraction dependencies (MarkItDown, openpyxl, PyMuPDF, pdfannots, and python-pptx)
are already declared in the package.

### Google Drive

The Drive helpers use Google's native **Drive API v3** client and OAuth libraries:

```python
file_id = ez.gfileid("book.docx", folderid)
ez.gdownload(file_id, "/tmp/book.docx")  # download the existing file; no remote creation
name, uploaded_id = ez.gupload("/tmp/book.docx", folderid)
files = ez.gls(folderid)                # [(name, id), ...], across all result pages
```

Uploaded files are downloaded unchanged. Native Google Docs/Sheets/Slides are
exported according to the destination extension supported by `gdownload`.
`gdelete` deletes permanently; `gcopy` copies files and `gmove` moves them between
folders. Upload updates the first non-trashed matching
name anywhere in Drive, rather than limiting that search to the destination folder.

`ez.gauth()` returns Google's native v3 service. Use `ez.gdownload(file_id, path)`
for downloads, or access the service directly:

```python
service = ez.gauth()
metadata = service.files().get(fileId=file_id, fields="id,name,mimeType").execute()
```

`ez.gauth()` requires `GDRIVE_KEY` imported from the package's private
`pysecrets.py` module. It does not read or write `gdrive_secrets.json`.
Client settings must contain an installed/web Google OAuth client configuration.
The cached token is reused and refreshed as needed.
Authentication does not change the working directory.

When no token is cached, the call opens your browser for Google login and consent,
then saves `gdrive_token.json` beside the installed module after authorization
succeeds. It does not create a separate `token.json`. Browser authorization requires
OAuth client settings in `GDRIVE_KEY`. Subsequent calls reuse the token and refresh it
when expired. Malformed tokens, failed refreshes, and write errors
are reported rather than silently restarting authorization. New credential files
are written atomically with owner-only permissions; never commit or share them.
Credential cache files are excluded from built source archives and wheels.
The helper requests full Drive access for its read/write/delete
operations. The package directory must be writable for credential caching.

Existing Web application OAuth clients can be reused without creating a new client.
Browser login selects the first supported entry in the client's `redirect_uris`:
`http://localhost:PORT/` or `http://127.0.0.1:PORT/` (also supported without the
trailing slash). The host, port, and trailing slash are preserved exactly.
The selected port must be free. If no supported entry exists, add one such as
`http://localhost:8080/` to the **same client's** authorized redirect URIs in
Google Cloud Console, then update `GDRIVE_KEY` to include
it. Desktop clients continue to use an automatically selected local port.

`ez.GCal()` similarly requires `GCAL_KEY` imported from `pysecrets.py` and passes
the settings directly to Google's OAuth flow without writing `gcal_secrets.json`.
It preserves the existing `gcal_token.pickle` cache beside the installed module,
reuses valid tokens, and saves refreshed tokens. Initial Calendar login uses
local port 8080. Neither helper changes the working directory. Existing
client-settings files are left untouched but are no longer used. Only load
Calendar pickle tokens from a trusted source.

## Maintaining the Function Catalog

The topic regions and function docstrings in [`ez/ez.py`](ez/ez.py) are the source
of truth for both the generated `ez.__doc__` catalog and the README function
catalog. Both list the same topics, functions, aliases, and summaries.
Each module-level function belongs
to a topic region and a nested region named after the function. Keep a concise
description on the first line of its docstring; existing parameter details and
examples follow it. Keep function aliases inside the same topic. Imported
convenience functions inside topic regions are listed with their source module.
Class methods and nested functions are not cataloged.

[`ez/prepublish.py`](ez/prepublish.py) reads this structure using only the Python
standard library, without importing `ez` or its optional runtime dependencies.
It replaces only the module's `__doc__` assignment and the README section between
the `BEGIN GENERATED FUNCTION CATALOG` and `END GENERATED FUNCTION CATALOG`
markers. Do not edit either generated catalog by hand; edit the source docstrings
or regions instead. Usage details outside the markers remain hand-maintained.

```bash
python ez/prepublish.py --docs-only   # regenerate both catalogs; do not bump the version
python ez/prepublish.py --check-docs  # exit nonzero if either catalog is stale or invalid
python ez/prepublish.py --help
```

Running the hook **without flags**, or with `--docs-only`, regenerates both catalogs
and the marked CLI entry points in [`pyproject.toml`](pyproject.toml). `--check-docs`
checks all three generated outputs without writing. All outputs are validated
before any are written. The hook no longer increments the version; version changes
belong to the publishing workflow below. Paths are relative to the hook, not the
current working directory.

Run the focused maintenance tests with:

```bash
python -m unittest discover -s tests
```

## Building and Publishing

Install [uv](https://docs.astral.sh/uv/getting-started/installation/) for release
work. The project uses the native `uv_build` backend; setuptools and Twine are no
longer needed. Package identity, dependencies, and the authoritative release
version live in [`pyproject.toml`](pyproject.toml). [`ez/version.py`](ez/version.py)
reads that version in a source checkout or uses installed distribution metadata.

To regenerate metadata and build **without publishing or bumping the version**:

```bash
uv run --no-project --python '>=3.11' ez/prepublish.py --docs-only
uv build
```

The build produces an sdist (`.tar.gz`) and a `py3-none-any.whl` wheel. The wheel
contains pure Python and works with supported Python versions on Windows, Linux,
Intel Macs, and ARM Macs, regardless of the build machine. Dependencies still need
compatible releases for the target platform, and OS-specific features retain
their existing limitations and dependency markers.

### PyPI authentication

The publishers prefer `UV_PUBLISH_TOKEN`. Otherwise they automatically read
`~/.pypirc`, using **only** its `[pypi]` section:

```ini
[pypi]
username = __token__
password = YOUR_PYPI_API_TOKEN
repository = https://upload.pypi.org/legacy/
```

Reuse an existing PyPI API token, preferably scoped to the `ez` project, or create
one in your [PyPI account settings](https://pypi.org/manage/account/token/).
`repository` is optional but must point to the standard PyPI upload URL if set.
Protect the file with `chmod 600 ~/.pypirc`; never commit it or the token.
Missing, malformed, or non-token credentials stop the release before preparation.
The token is passed to uv through its process environment, not command-line
arguments or release logs.

This `.pypirc` support is implemented by the shared
[`scripts/publish.py`](scripts/publish.py) helper, **not by uv itself**. Standalone
`uv publish` needs uv-native credentials, such as `UV_PUBLISH_TOKEN`.
A Finder-launched app normally does not inherit terminal exports; the `.pypirc`
fallback lets both entry points use the same existing credentials.

### Full release

From a terminal, run:

```bash
bash publish.sh
bash publish.sh --help
```

The shell script can also be run directly as `./publish.sh`.

Alternatively, open [`Publish.app`](Publish.app) in the checkout. Its
[`resource script`](Publish.app/Contents/Resources/script) contains a separate,
manually maintained copy of [`publish.sh`](publish.sh), matching the original app
arrangement. It does not invoke or require the external shell script, but still
requires the checkout's publishing helper, prepublish hook, and package files.
When changing either shell script, update the other copy too; a regression test
checks their current parity. Both resolve the checkout from their own locations,
including paths with spaces.

The publisher loads `~/.bash_profile` if present and checks for `uv`, Git, and your
existing `ezupdate` command/function/alias before preparing a release. It then:

1. Validates credentials and the version format.
2. Runs prepublish to update catalogs and CLI entry points.
3. Uses `uv version --bump COMPONENT --frozen`, preserving the existing numbering:
   patch normally (`11.8.8 → 11.8.9`), minor when patch is 9 (`11.8.9 → 11.9.0`),
   and major when both minor and patch are 9 (`11.9.9 → 12.0.0`). Minor and patch
   must remain single digits. uv updates the version without locking or syncing.
4. Builds both artifacts in a fresh temporary directory, retains them in `dist/`,
   then deletes older `ez` source archives and wheels so only the latest release's
   two artifacts remain. Cleanup occurs only after a successful build and copy;
   unrelated files and directories are not removed. It publishes **only the new
   files** with `uv publish`. Existing files for the new version are not overwritten.
5. Stages **all checkout changes**, commits, pushes to `origin master`, then runs
   `ezupdate` three times, preserving the existing post-release workflow.
6. Prints the distribution version and files in `dist/`, followed by the locally
   installed `ez` version and installation location from `uv pip show ez`.
   This reports uv's selected Python environment, which may differ from the
   environment your `ezupdate` command upgrades. A missing package or reporting
   error is shown explicitly and stops the script rather than reporting success.

Errors stop subsequent steps. A failed build/upload may leave the version bumped
and artifacts in `dist/`; inspect the state before retrying. A partial upload or a
later Git/upgrade failure does **not** undo files already published to PyPI.
To retry an upload, use the exact retained artifacts and provide uv-native
authentication; do not blindly rerun the full publisher, which bumps again.
Use prepublish's check/docs-only modes, not the publisher, for documentation work.
